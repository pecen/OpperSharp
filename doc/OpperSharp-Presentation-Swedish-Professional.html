OpperSharp

C# SDK för Opper AI v2 API

En produktionsklar implementation för .NET-utvecklare

Presentationen handlar om OpperSharp - en C# SDK jag har utvecklat för Opper AI v2 API. Opper är en AI-plattform som erbjuder Functions, RAG (Retrieval-Augmented Generation), Chat, Tracing, Agents, Embeddings, OCR och mer. De har officiella SDKs för Python och TypeScript, men ingenting för .NET-ekosystemet. OpperSharp fyller detta gap och ger .NET-utvecklare fullständig tillgång till v2 API:et med alla nya funktioner.

Bakgrund

Opper AI erbjuder officiella SDKs för:

  • Python
  • TypeScript/JavaScript

För .NET-utvecklare finns inget motsvarande verktyg.

Opper AI är en plattform för AI-integration som tillhandahåller olika tjänster. De har byggt SDKs för Python och TypeScript, vilket täcker en stor del av utvecklarcommunity. Men för oss som arbetar i .NET-miljöer - vilket är vanligt inom enterprise, särskilt i finanssektorn och hos större företag - fanns det inget motsvarande verktyg. Alternativet var att arbeta direkt mot REST API:et, vilket innebär mycket mer arbete och mindre typsäkerhet.

Vad är OpperSharp?

En komplett C# SDK som tillhandahåller:

  • Fullständig v2 API-täckning (11 API-endpoints)
  • Typsäkerhet och IntelliSense-stöd
  • Async/await-baserad implementation
  • Filbaserade kunskapsbaser med PDF/CSV-stöd
  • Model aliases för automatisk fallback
  • OCR, Rerank, Analytics och mer
OpperSharp är en fullständig implementation av Opper v2 API i C#. SDK:n täcker alla 11 API-endpoints i v2, vilket ger komplett funktionalitet. v2 API introducerade viktiga förbättringar: filbaserade kunskapsbaser istället för document-indexing, model aliases för automatisk fallback vid fel, OCR för dokumentprocessering, och mycket mer. Typsäkerheten är en viktig fördel - fel upptäcks vid kompilering istället för vid runtime, och IntelliSense ger dokumentation direkt i utvecklingsmiljön.

Arkitektur

Modulär struktur med fullständig v2 API-täckning:

  • OpperSharp.Core - HTTP-klient och grundfunktionalitet
  • Functions - AI-funktionsanrop
  • Knowledge - Filbaserade kunskapsbaser (v2)
  • Chat - Konversations-API
  • Datasets - Träningsdata (v2)
  • Embeddings - Vektorgenererering (v2)
  • Models - Model aliases med fallback (v2)
  • OCR - Dokumentprocessering (v2)
  • Rerank - Sökoptimering (v2)
  • Analytics - Användningsmetrik (v2)
  • Spans - Distributed tracing
  • Agents - Multi-steg AI-agenter
Arkitekturen är utökad för v2 API med sex nya klienter: Knowledge (ersätter Indexes), Datasets, Embeddings, Models, OCR, Rerank och Analytics. Knowledge-klienten är en viktig förändring - v2 använder filuppladdning (PDF, CSV, TXT) istället för document-indexing. Detta ger mer flexibilitet och bättre integrering med verkliga dokument. Models-klienten hanterar model aliases, vilket låter dig definiera fallback-modeller om primärmodellen är otillgänglig. Allt är byggt för .NET 8.0 med nullable reference types för maximal typsäkerhet.

Grundläggande användning

using OpperSharp;

var client = new OpperClient("api-key");

var result = await client.Functions.CallAsync(
    "function-name",
    new { text = "input data" }
);

Console.WriteLine(result.Message);
Detta är den enklaste formen av användning. Man skapar en OpperClient med sin API-nyckel och kan sedan anropa AI-funktioner. Jämfört med att använda REST API direkt, där man måste hantera HTTP-klienten själv, sätta headers, serialisera JSON manuellt och hantera fel, reduceras koden med cirka 90%. Typsäkerheten innebär att fel i funktionsnamn eller parametrar upptäcks direkt i utvecklingsmiljön.

Jämförelse: REST API vs OpperSharp

REST API

  • Skapa och konfigurera HttpClient
  • Sätta headers manuellt
  • JSON-serialisering
  • Manuell felhantering
  • Deserialisering av svar
  • Ca 40-50 rader kod per operation

OpperSharp

  • Instantiera OpperClient
  • Anropa metod
  • Ca 5 rader kod per operation
Denna jämförelse visar den praktiska fördelen med SDK:n. När man arbetar direkt mot REST API måste man hantera alla HTTP-detaljer själv. Detta inkluderar att skapa HttpClient, konfigurera headers för autentisering och content type, serialisera request body till JSON, skicka request, hantera HTTP-fel (404, 500 etc), och deserialisera response body. Med OpperSharp hanteras allt detta automatiskt. SDK:n inkluderar även retry-logik för transient errors och hantering av rate limiting. Den kod-reduktion på 90% innebär mindre kod att underhålla och färre möjligheter för fel.

Functions API

// Enkelt anrop
var result = await client.Functions.CallAsync(
    "extract-entities",
    new { text = documentText }
);

// Med RAG-context
var ragResult = await client.Functions.CallAsync(
    "answer-question",
    new { question = userQuestion },
    new OpperCallOptions
    {
        Context = new() { ["knowledge_base"] = "documentation" }
    }
);
Functions API är kärnan i Opper. Man definierar AI-funktioner i Opper-plattformen med prompts och konfiguration, och anropar dem sedan programmatiskt. Det första exemplet visar ett enkelt anrop där man skickar in text och får tillbaka ett resultat. Det andra exemplet visar RAG (Retrieval-Augmented Generation). Genom att ange en context med knowledge_base kommer Opper att först hämta relevant information från den angivna kunskapsbasen, och sedan använda den informationen som context när AI-funktionen körs. Detta är kraftfullt för att bygga Q&A-system över egen data, där svaren baseras på faktisk dokumentation istället för AI-modellens förtränade kunskap.

Streaming

await foreach (var chunk in client.Functions.StreamAsync(
    "generate-text",
    new { topic = "AI development" }
))
{
    Console.Write(chunk.Delta);
}

Använder IAsyncEnumerable för idiomatisk C#-kod

Streaming är viktigt för användarupplevelsen när man genererar längre texter. Istället för att vänta på hela svaret kan man visa text allt eftersom den genereras. OpperSharp använder IAsyncEnumerable, vilket är den idiomatiska C#-lösningen för asynkron streaming. Detta integreras naturligt med await foreach. Under huven använder SDK:n Server-Sent Events (SSE) för att ta emot chunks från Opper API. Varje chunk innehåller en Delta-property med nästa del av texten. Detta är särskilt användbart i chatbot-scenarion eller när man genererar längre dokument.

Kunskapsbaser och RAG (v2)

// Skapa kunskapsbas
await client.Knowledge.CreateAsync("documentation");

// Ladda upp fil
using var fileStream = File.OpenRead("manual.pdf");
await client.Knowledge.UploadFileAsync(
    "documentation",
    "manual.pdf",
    fileStream,
    "application/pdf"
);

// Använd med Functions (integrerad RAG)
var answer = await client.Functions.CallAsync(
    "answer-question",
    new { question = "How do I configure auth?" },
    new OpperCallOptions
    {
        Context = new() { ["knowledge_base"] = "documentation" }
    }
);
v2 API introducerade Knowledge Bases som ersätter det gamla Indexes-konceptet. Den stora skillnaden är att v2 använder filuppladdning istället för document-indexing. Man kan ladda upp hela PDF:er, CSV-filer eller textfiler. Opper hanterar parsing, chunking och embedding-generering automatiskt. Integrationen med Functions är sömlös - genom att ange knowledge_base i Context kommer relevanta delar av de uppladdade filerna att användas som kontext. Detta är mycket mer praktiskt än det gamla systemet där man själv fick chunka dokument och indexera dem separat.

Chat API

var response = await client.Chat.CreateAsync(
    new ChatRequest
    {
        Messages = new List
        {
            new() {
                Role = "user",
                Content = "Explain dependency injection"
            }
        },
        ParentSpanId = spanId
    }
);

Console.WriteLine(response.Message);
Chat API används för konversationsbaserade applikationer. Till skillnad från Functions som är mer single-shot, är Chat designat för flervägsdialog. Man skickar in en lista av meddelanden som representerar konversationshistoriken. Varje meddelande har en Role (system, user eller assistant) och Content. ParentSpanId är valfritt men rekommenderat - det kopplar chat-anropet till ett span för tracing, vilket gör det möjligt att följa hela konversationsflödet i Oppers UI. För att fortsätta en konversation lägger man till svaret i message-listan och skickar in den uppdaterade listan vid nästa anrop.

Datasets API (v2)

// Skapa träningsdata
await client.Datasets.CreateEntryAsync(
    "customer-support-training",
    input: new { question = "How do I reset my password?" },
    output: new { answer = "Click 'Forgot Password' on login page..." },
    comment: "Common support question"
);

// Lista entries
var entries = await client.Datasets.ListEntriesAsync(
    "customer-support-training",
    limit: 100
);
Datasets API är nytt i v2 och används för att hantera träningsdata för fine-tuning av modeller. Man kan skapa dataset entries med input och output, samt valfria kommentarer för dokumentation. Detta är användbart för att bygga upp träningsdata över tid baserat på faktisk användning, för att sedan fine-tuna modeller för specifika användningsfall.

Embeddings API (v2)

// Generera embeddings
var embeddings = await client.Embeddings.CreateAsync(
    "Text to convert to vector",
    model: "azure/text-embedding-3-large"
);

Console.WriteLine($"Dimensions: {embeddings.Count}");

// Batch-generering
var batchResponse = await client.Embeddings.CreateBatchAsync(
    new[] { "First text", "Second text", "Third text" },
    model: "azure/text-embedding-3-large"
);
Embeddings API låter dig generera vektorrepresentationer av text. Detta är användbart om du vill bygga egen semantisk sökning, eller integrera med externa vektordatabaser. Batch-funktionen är effektiv för att generera embeddings för många texter samtidigt.

Models API med Aliases (v2)

// Skapa model alias med fallback
await client.Models.CreateAliasAsync(
    "reliable-gpt4",
    fallbackModels: new List
    {
        "gpt-4",
        "gpt-4-turbo",
        "gpt-3.5-turbo"
    },
    description: "GPT-4 with automatic fallback"
);

// Använd alias i Functions
var result = await client.Functions.CallAsync(
    "analyze-text",
    new { text = input },
    new OpperCallOptions { Model = "reliable-gpt4" }
);
Models API är en kraftfull v2-funktion som låter dig skapa model aliases med automatisk fallback. Om den primära modellen (gpt-4) är otillgänglig eller överbelastad, faller systemet automatiskt tillbaka på nästa modell i listan. Detta ger mycket högre tillförlitlighet i produktionssystem utan att du behöver hantera retry-logik själv.

OCR API (v2)

// Processa dokument med OCR
var ocrResult = await client.Ocr.ProcessAsync(
    new OpperOcrRequest
    {
        Model = "gpt-4-vision",
        Document = documentBytes,
        Instructions = "Extract all text and preserve formatting"
    }
);

Console.WriteLine(ocrResult.Text);

// Lista tillgängliga OCR-modeller
var models = await client.Ocr.ListModelsAsync();
OCR API är nytt i v2 och använder vision-modeller för att extrahera text från dokument och bilder. Man kan ge instruktioner för hur texten ska extraheras, till exempel att bevara formatering eller extrahera specifika fält. Detta är användbart för att processa skannade dokument, fakturor, kvitton eller handskrivna anteckningar.

Rerank API (v2)

// Rerank sökresultat baserat på relevans
var reranked = await client.Rerank.RerankAsync(
    query: "best practices for authentication",
    documents: searchResults,
    model: "rerank-model",
    topK: 5
);

foreach (var result in reranked.Results)
{
    Console.WriteLine($"Score: {result.Score}, Doc: {result.Document}");
}
Rerank API används för att optimera sökresultat. Efter en initial sökning kan man använda Rerank för att omrangordna resultaten baserat på semantisk relevans till query. topK-parametern låter dig begränsa antalet resultat till de mest relevanta. Detta förbättrar kvaliteten på RAG-system avsevärt genom att säkerställa att de mest relevanta dokumenten används som kontext.

Analytics API (v2)

// Hämta användningsstatistik
var usage = await client.Analytics.GetUsageAsync(
    fromDate: DateTime.Now.AddDays(-30),
    toDate: DateTime.Now,
    granularity: "day",
    fields: new List { "tokens", "cost", "requests" },
    groupBy: new List { "function", "model" }
);

foreach (var entry in usage.Data)
{
    Console.WriteLine($"{entry.Date}: {entry.Requests} requests");
}
Analytics API ger insikt i användning och kostnader. Man kan hämta statistik över tokens, kostnad, antal requests, grupperat per funktion eller modell. Granulariteten kan sättas till dag, vecka eller månad. Detta är kritiskt för cost tracking och för att förstå användningsmönster i produktionssystem.

Spans för tracing

var span = await client.Spans.CreateAsync(
    "user-query-flow",
    new { query = userInput }
);

try
{
    var result = await ProcessQuery(userInput, span.Id);
    await client.Spans.UpdateAsync(span.Id, new { result });
}
catch (Exception ex)
{
    await client.Spans.UpdateAsync(span.Id, new { error = ex.Message });
}
Spans är Oppers implementation av distributed tracing. Konceptet kommer från OpenTelemetry och distributed systems. Man skapar ett parent span när en operation börjar, och kan sedan skapa child spans för varje delsteg. Detta bygger upp en träd-struktur av operationer. När operationen är klar uppdaterar man spanet med resultatet. Vid fel uppdaterar man med felinformation. I Oppers UI kan man sedan se hela flödet av spans, vilket är ovärderligt för debugging och för att förstå vad som händer i komplexa AI-operationer. Spans kan också användas för cost tracking - varje AI-anrop kan kopplas till ett span och kostnaden aggregeras.

Agents

public class DatabaseTools
{
    [Tool("Query the user database")]
    public async Task QueryUsers(string criteria)
    {
        // Implementation
        return JsonSerializer.Serialize(users);
    }
}

var agent = new Agent(client, new AgentOptions
{
    FunctionPath = "customer-service-agent",
    Tools = Agent.DiscoverTools()
});

var result = await agent.RunAsync(
    new { request = "Find all premium users" }
);
Agents är den mest avancerade funktionen. En agent är en AI som kan använda verktyg (tools) för att lösa uppgifter. Man definierar verktyg som C#-metoder och markerar dem med Tool-attributet. Attributet innehåller en beskrivning som AI:n använder för att förstå vad verktyget gör. Agent.DiscoverTools använder reflection för att hitta alla metoder med Tool-attributet och registrerar dem automatiskt. När agenten körs analyserar AI:n uppgiften, bestämmer vilka verktyg som behövs, anropar dem, och använder resultatet för att fortsätta. Detta kan ske i flera steg. MaxIterations i AgentOptions förhindrar oändliga loopar. Agenten har också inbyggd integration med Spans för att tracka vad som händer.

Felhantering

try
{
    var result = await client.Functions.CallAsync(...);
}
catch (OpperException ex)
{
    // API-specifika fel (4xx, 5xx)
    Console.WriteLine($"API error: {ex.StatusCode}");
    Console.WriteLine(ex.Message);
}
catch (HttpRequestException ex)
{
    // Nätverksproblem
}
SDK:n har strukturerad felhantering. OpperException kastas för API-fel och innehåller HTTP-statuskoden och response body. För transient errors (429 Rate Limit, 5xx Server Errors) har SDK:n inbyggd retry-logik med exponential backoff. Detta hanteras automatiskt och är transparent för användaren. HttpRequestException kastas för nätverksproblem som timeout eller connection failures. För production-kod rekommenderas att implementera ytterligare error handling och logging runt SDK-anrop.

v2 Migration & Backwards Compatibility

// Deprecated (v1) - fungerar fortfarande
await client.Indexes.IndexAsync("my-index", content);

// Rekommenderat (v2) - filbaserad approach
await client.Knowledge.CreateAsync("my-kb");
using var file = File.OpenRead("doc.pdf");
await client.Knowledge.UploadFileAsync("my-kb", "doc.pdf", file, "application/pdf");

IndexesClient är deprecated men fungerar för backwards compatibility

OpperSharp hanterar v2-migrationen smidigt. Det gamla Indexes API är markerat som deprecated men fungerar fortfarande för backwards compatibility. Man får compiler warnings om man använder det. För ny kod rekommenderas Knowledge API som använder v2:s filbaserade approach. Detta ger en mjuk migreringsväg - befintlig kod fungerar medan ny kod kan använda v2-funktionalitet.

Komplett exempel: RAG-baserad kunskapsbas (v2)

// 1. Skapa kunskapsbas och ladda upp dokumentation
await client.Knowledge.CreateAsync("docs");

using var fileStream = File.OpenRead("documentation.pdf");
await client.Knowledge.UploadFileAsync(
    "docs",
    "documentation.pdf",
    fileStream,
    "application/pdf"
);

// 2. Användare ställer fråga
var answer = await client.Functions.CallAsync(
    "answer-from-docs",
    new { question = "How do I configure the agent?" },
    new OpperCallOptions
    {
        Context = new() { ["knowledge_base"] = "docs" }
    }
);

// 3. Svar baserat på faktisk dokumentation
Console.WriteLine(answer.Message);
Detta är ett typiskt användningsfall för RAG med v2 API - en kunskapsbas över egen dokumentation. Först skapar man en kunskapsbas och laddar upp PDF-filer. Opper hanterar parsing, chunking och embedding-generering automatiskt. När en användare ställer en fråga anropas en AI-funktion med knowledge_base i context. Opper hämtar då relevanta delar från de uppladdade filerna. De hämtade dokumentdelarna används som context för AI-funktionen, som ger svar baserat på faktisk dokumentation. v2:s filbaserade approach är mycket enklare än v1:s document-indexing.

NuGet-paket planeras beroende på intresse

Just nu distribueras OpperSharp via GitHub. Man klonar repot, bygger projekten, och refererar dem i sitt eget projekt. Alternativt kan man kopiera in projekten i sin egen solution för tätare integration. NuGet-publicering är något jag överväger om det finns tillräckligt intresse. Det innebär ett åtagande att underhålla paketet över tid. Projektet är MIT-licensierat så det är fritt att använda och modifiera.

Rekommendationer

  • Använd using-statements för OpperClient (IDisposable)
  • Konfigurera timeouts för långvariga operationer
  • Implementera spans för observability
  • Använd Oppers cache-funktion där det är relevant
  • Bygg gränssnitt för testbarhet
OpperClient implementerar IDisposable för att hantera HTTP-connections korrekt. Använd using-statements eller dependency injection med scoped lifetime. För streaming-operationer eller långsamma AI-anrop kan man behöva sätta högre timeout än standard. Spans bör implementeras från början. Det är svårare att lägga till i efterhand, och observability är kritiskt för produktionssystem. Opper har caching på serversidan. Genom att sätta Cache = true i OpperCallOptions kan identiska anrop returnera cachade resultat, vilket sparar både tid och kostnad. För unit testing rekommenderas att skapa ett interface för OpperClient och injicera det, så att man kan mocka API-anrop i tester.

Teknisk implementation

  • .NET 8.0 med nullable reference types
  • Newtonsoft.Json för serialisering
  • HttpClient med retry-logik
  • IAsyncEnumerable för streaming
  • Reflection för tool discovery
  • Fullständig v2 API-implementation (11 endpoints)
  • Modulär arkitektur med separata Models-projekt
OpperSharp är byggt för .NET 8.0, som är en Long Term Support-version. Nullable reference types är aktiverat i alla projekt för att fånga null-relaterade fel vid kompilering. Newtonsoft.Json används för serialisering med flexibel hantering av JSON-properties. Retry-logiken hanterar transient errors automatiskt med exponential backoff. IAsyncEnumerable är .NET:s idiomatiska sätt att hantera asynkron streaming. Alla 11 v2 API-endpoints är implementerade, inklusive nya funktioner som Knowledge, Datasets, Embeddings, Models, OCR, Rerank och Analytics.

Begränsningar

  • Kräver Opper API-konto och API-nyckel
  • Inte officiellt supportad av Opper
  • Ännu inte publicerad på NuGet
  • Dokumentation finns primärt i kodkommentarer
  • Test coverage kunde vara mer omfattande
För transparensens skull finns det några begränsningar att vara medveten om. OpperSharp kräver ett Opper-konto. Opper har en free tier för utveckling och testning, men production-användning medför kostnader baserat på användning. Detta är inte en officiell SDK från Opper, vilket innebär att supporten kommer från mig och eventuell community, inte från Oppers team. SDK:n är inte på NuGet än, vilket innebär manuell hantering av projektreferenser. Dokumentation finns i form av XML-kommentarer i koden som ger IntelliSense, men mer omfattande guides och tutorials skulle vara värdefulla. Test coverage finns för huvudfunktionaliteten men inte för alla edge cases.

Frågor

Vanliga frågor som kan komma upp: Q: Varför inte bara använda OpenAI API direkt? A: Opper tillhandahåller mer än bara LLM-anrop. Det inkluderar RAG-infrastruktur, tracing, agent framework och hantering av prompts. Detta är värdefulla funktioner för produktionssystem. Q: Vad kostar Opper? A: Opper har usage-baserad prissättning. Det finns en free tier för utveckling. För production beror kostnaden på användning och vilka AI-modeller man använder. Q: Kan jag self-hosta? A: Nej, Opper är en managed cloud service. För vissa företag kan detta vara en begränsning, men det innebär också att man slipper hantera infrastruktur. Q: Prestanda? A: Prestanda beror på Opper API och underliggande AI-modeller. Typiska function calls tar 200-1000ms beroende på komplexitet. Streaming ger lägre perceived latency. Q: Stöd för äldre .NET-versioner? A: SDK:n är byggd för .NET 8, men bör fungera på .NET 6 och 7 med mindre justeringar. .NET Framework stöds inte.
